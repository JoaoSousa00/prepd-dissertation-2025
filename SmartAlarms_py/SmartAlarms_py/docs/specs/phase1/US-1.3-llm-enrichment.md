# Specification ID: US-1.3

## 1) Header

- **Title:** Adding LLM enrichment for incident analysis
- **Phase:** Phase 1
- **Owner:** Spec Architect
- **Status:** Implemented
- **Related documents:** `docs/requirements.md`, `docs/architechture.md`

## 2) Problem Statement

Once base incident data is available, the next step is to enrich it with summaries, related incident hints, and mitigation suggestions generated by an LLM.

## 3) User Story

> As a support analyst, I want the incident data to be enriched with LLM-generated guidance, so that I can understand possible causes and actions faster.

## 4) Scope

### In scope
- LLM-driven summary generation
- Mitigation suggestion generation
- Related incident correlation hints from the incident context

### Out of scope
- Metrics
- Logs analysis
- MCP integration
- Observability beyond basic request handling

## 5) Acceptance Criteria

| ID | Given | When | Then |
|----|-------|------|------|
| CA-1 | Base incident data is available | The analysis runs | A natural-language summary is generated |
| CA-2 | Incident context is available | The analysis runs | Mitigation suggestions are generated |
| CA-3 | Similar historical incidents exist | The analysis runs | Related incident references are included when available |
| CA-4 | The LLM is unavailable | The analysis runs | The service degrades gracefully and still returns the base incident data |

## 6) Functional Design

- Entry point: domain layer after base incident fetching.
- Inputs: base incident data and optional historical context.
- Outputs: enriched incident data with summary and mitigation fields.
- Happy path: domain builds a bounded prompt from incident context, calls the LLM infrastructure adapter, and merges the returned enrichment into the incident response.
- Error path: if the LLM fails, preserve the base incident response.

## 7) Data and Integration Design

- External dependencies: LLM adapter.
- Cache usage: reuse normalized context if already fetched in the request flow.
- Identity/permissions assumptions: server-side credentials only.

## 7a) Environment Configuration

The LLM gateway connection to GAIA is fully configurable via environment variables. See `.env_template` for complete list.

### Required Configuration

| Variable | Purpose | Notes |
|----------|---------|-------|
| `GAIA_LLM_ENDPOINT` | Base URL for the GAIA LLM gateway | Example: `https://gaia.api/v1` |
| `GAIA_MODEL` | Model name to send to the gateway | Example: `gpt-4` |
| `GAIA_AUTH_ENDPOINT` | OAuth token endpoint for machine-to-machine auth | Example: `https://auth.api/token` |
| `LLM_API_KEY` | OAuth client ID from webEAM token JSON | Used for OAuth client credentials flow |
| `LLM_CLIENT_SECRET` | OAuth client secret from webEAM token JSON | Used for OAuth client credentials flow |
| `CA_CERT_PATH` | Local path to BMW CA bundle | Example: `/path/to/ca/bundle.pem` |
| `CA_CERT_URL` | Download URL for BMW CA bundle | Used for certificate rotation/updates |

### Optional Configuration

| Variable | Default | Purpose | Notes |
|----------|---------|---------|-------|
| `LLM_X_API_KEY` | (unset) | Gateway `x-apikey` header | Falls back to `LLM_API_KEY` when unset |
| `LLM_GATEWAY_ENABLED` | `true` | Enable/disable LLM gateway | When `false`, uses stub behavior |
| `LLM_MAX_RETRIES` | `3` | Retry count for transient failures | Applies exponential backoff |
| `LLM_RETRY_BASE_DELAY_SECONDS` | `1.0` | Base delay for exponential backoff | Backoff formula: `base * (2 ^ attempt)` |
| `LLM_DEFAULT_MAX_TOKENS` | `2048` | Default max tokens for LLM responses | Used when model config leaves it unset |
| `LLM_REQUEST_TIMEOUT_SECONDS` | `30.0` | Timeout for chat completion requests | Empty, `0`, or `none` disables it |
| `LLM_AUTH_TIMEOUT_SECONDS` | `10.0` | Timeout for OAuth token requests | `0` or `none` disables it |

## 8) Token Efficiency Design

- Build prompts only from incident-relevant context.
- Keep the prompt small and deterministic.
- Avoid repeated calls for the same incident data within one request.

## 9) Observability

- Minimal analysis logging only.

## 10) Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Verbose prompts increase cost | Higher latency and token use | Bound the prompt to the incident scope |
| LLM failure blocks the response | Lost usefulness | Keep the base incident data as the fallback |

## 12) Implementation Notes

### Completed Implementation Files

**Domain Layer:**
- `src/domain/llm.py` - LLM gateway protocol, domain models, and exception hierarchy

**Infrastructure Layer:**
- `src/infrastructure/llm_config.py` - Configuration management for GAIA LLM gateway
- `src/infrastructure/llm_gateway.py` - GaiaLlmGatewayAdapter with OAuth, retries, timeouts, response parsing

**Tests:**
- `tests/test_llm_config.py` - 20 tests for configuration validation
- `tests/test_llm_gateway.py` - 15 tests for authentication, retries, parsing, error handling

### Key Implementation Details

- OAuth token caching with TTL (90% of `expires_in`)
- Exponential backoff retry logic for transient failures
- Prompt building optimized for token efficiency
- JSON and raw text response handling with fallback
- Gateway disable feature for stub/offline operation
